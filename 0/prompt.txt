## 1. The new table

### Recommendation: one table, `eval_runs`, cached report as **JSONB in the row**

**Grain:** one row per *measured fight* (`run_fight_id`), `UNIQUE`. Because a fight's pipeline never re-runs, "fight" and "pipeline version" are 1:1 for scored runs — the trend line's x-axis is a sequence of different `ai_labeled` fight ids over the same reference. Re-scoring is an `UPDATE` in place (a score at a different tolerance isn't comparable to the one it replaces anyway).

**`reference_fight_id` is nullable.** A row with it NULL is a label-free measurement of one fight (sanity + corner accuracy only) — that's what serves brief §F for fights 42/44/58 that have no reference pair. A row with it set is a scored fixture (§E). One table, one row = one fight's complete measurement record.

**JSONB, not `ai/eval/reports/`.** Four reasons:
1. The backend cannot reach `ai/`'s filesystem conventions cleanly — it runs in a different venv with `AI_DIR` as an env override, and would need a whole path-resolution + file-serving layer mirroring `_resolve_video_path`.
2. Atomicity. The comparability keys (`tolerance_secs`, `reference_fight_id`, `git_sha`) live in columns *beside* the blob, so a SQL query can refuse a comparison without parsing JSON, and the row can never disagree with the file it points at.
3. The trend query is one statement: `SELECT scored_at, score_report-&gt;'strikes'-&gt;'detection' FROM eval_runs WHERE reference_fight_id = :r AND tolerance_secs = :t ORDER BY scored_at` — no fan-out of file reads, and pooled TP/FP/FN is `SUM((score_report-&gt;'strikes'-&gt;'detection'-&gt;&gt;'tp')::int)`.
4. Size is trivial: the unbounded parts are `missed`/`spurious`, bounded here at 227 + 147 entries.

Keep `report_io.save_report(path)` and the `--json` flag exactly as they are — `ai/eval/baselines/*.json` stays the git-committed artifact. `report_path` records where that copy went, so the ledger can show "exported". JSONB is the dashboard's source of truth; disk is the archive. Not either/or.

**Rejected alternative:** splitting into `eval_runs` (pairing) + `eval_reports` (blobs, one per kind). It buys a clean re-score history but costs a join on every dashboard query and a second place for the comparability keys to drift. Revisit only if you start wanting multiple tolerances retained per run.

```python
    Only call this where a person is required — i.e. comparing against a
    different fight's fight_events.fighter_id. Never for the label-&gt;keypoint
    join, which must stay on the raw slot (see this class's corner_swaps
    docstring).
    """
    if any(s.contains(frame) for s in self.corner_swaps):
        return "blue" if slot_fighter == "red" else "red"
    return slot_fighter
```

### The live-vs-cached boundary

**The backend must never import `ai/eval`.** It runs in a separate venv (`pipeline_runner.AI_PYTHON`), and `score.py` pulls numpy + scipy, `corner_accuracy.py` pulls cv2, and everything under `eval/` imports `ai/database.py`'s own `SessionLocal`. `pipeline_runner.py` already establishes the boundary: cross-venv work is a subprocess that writes JSON.

That draws the line cleanly:

- **Live SQL** — anything expressible over `fights` / `fight_events` / `rounds` / `fighter_frames`: sections A, B, C, D, G2 and the tolerance ceiling in G1.
- **Cached (`eval_runs` JSONB)** — anything that needs `ai/eval` code to run: score (E), sanity (F1), corner accuracy (F2), agreement ceiling and swap recall (G1).

Every live query must carry an explicit `source`/`kind` filter — `backend/CLAUDE.md`'s standing rule for `fight_events`, and the one most likely to be broken by a new aggregate.
